01這是什麼・什麼時候用

/demo-cycle 是 portfolio-dash 的「以 demo 為規格」開發迴圈。 它的每一個階段都只產出一份可以點的自足 HTML：主張要嘛當場量給你看， 要嘛當場跟真引擎對帳給你看，不靠文字斷言。

沒有這套流程時

規格寫成文字 → 你我各自解讀 → 做出來不是你要的 → 回頭吵「當初講的是什麼意思」。稽核也一樣：讀程式碼推出根因， 症狀對、根因錯，照著改等於白改。

有這套流程時

規格是一個你點得動的 demo，前後可切換；稽核的每條發現都附 在跑著的實例上量到的數字，根因標明「已驗證」或「推測待驗」。 你在核准前就知道哪幾項可能變形。

它為什麼存在：2026-07-25 的全站稽核，13 條發現的症狀全對， 但有 4 條的根因是錯的——因為那 4 條是「讀程式碼推出來的」。 照原建議實作，2 條完全無效、1 條改錯地方、1 條會產生迴歸。 probe_live.py 就是這件事的修正：去量，不要猜。

04工具一 css：讀碼讀不出來的那件事

CSS 到底哪一條宣告勝出，讀檔案是問不出答案的。 兩個機制專門騙人：同特異性時後面的贏，以及 @media 不貢獻任何特異性。 v0.1.24 的 M1、M2 兩條根因就是栽在這裡。

.\.venv\Scripts\python.exe .claude\skills\demo-cycle\tools\probe_live.py css `
    http://127.0.0.1:8477 --selector ".kpi-band" --prop grid-template-columns --width 1257

它會印出所有命中的宣告（依原始碼順序）、各自的特異性、 當前寬度下 @media 條件是否成立、誰真的勝出，並在踩到陷阱時直接點名。 下面是這條指令在本機的真實輸出節錄：

   (0,1,0) #0   .kpi-band  =>  repeat(8, 1fr)
   (0,2,0) #1   .kpi-band.v2  =>  1.15fr 1.3fr 1.05fr 1.25fr 1.25fr
   (0,1,0) #2   .kpi-band  @media (max-width: 1280px)  =>  repeat(4, 1fr)
-> (0,2,0) #3   .kpi-band.v2  @media (max-width: 1280px)  =>  repeat(4, 1fr)
 x (0,1,0) #8   .kpi-band  @media (max-width: 760px)  =>  1fr 1fr   (condition false at this width)

  WINNER: .kpi-band.v2 @media (max-width: 1280px) -> repeat(4, 1fr)

實驗：同一段 CSS，三種寫法，看 getComputedStyle 當場改變

下面是真的 iframe，跑真的瀏覽器級聯——不是模擬。 「斷點」用 620px 代表真實的 1280px，機制完全相同。把滑桿拉到 620 以下觀察。

工具講的話意思你該做什麼
loses on SOURCE ORDER 同特異性，靠出現順序輸掉 改那條勝出的（移除或收窄），改輸家沒有用
media queries add NO specificity 斷點被無條件規則壓過，形同不存在 把斷點的選擇器提升到同等或更高（補上 .v2）

computed != winning declaration 簡寫／繼承／動畫介入了 以 computed 為準

08使用技巧

流程上的

技巧說明
先量，再寫字 任何一條發現在進報告之前，先有一行 probe_live 的輸出。 沒量到的就標推測待驗，不要混進已驗證的裡面
症狀與根因分兩層寫 症狀是量測（幾乎不會錯），根因是推論（會錯）。分開寫，你核准時才知道風險在哪
金額別自己重算 成本、損益、費稅、股利、匯兌、XIRR 交給 /stress-audit， 在報告裡引用它的 fail=0。這裡重算等於多一套會漂移的帳
通過項目也要寫 只列問題的報告會扭曲系統的實際狀態
一次只改一件事，改完立刻 verify verify_report.py 很快；把它當 gate 用，不要累積十個改動再一起驗
分歧要往三個地方寫 報告（當次）、CHANGELOG.md（你每次發版都會看）、 LESSONS_LEARNED.md（只在它是一「類」錯誤時，不是每個個案都寫）

操作上的

技巧說明
用 PowerShell，不要用 Git Bash MSYS 會把開頭是 / 的參數改寫成 Windows 路徑， --pages / 會變成 /C:/Program Files/Git/ 而安靜地探測錯的網址。 非用不可時加 MSYS_NO_PATHCONV=1
一定要 PYTHONIOENCODING=utf-8 否則繁體中文走預設 cp1252 主控台會 UnicodeEncodeError 中斷
先量 1257px，再量 390px 1257 是你實際回報過的視窗寬；中間寬度的斷點失效只在那附近看得到
--click 之前先確認是可丟棄實例 它會真的按下去。看到 DEAD? 先想「是不是本來就啟用的分頁」
報告要能離線開 圖片轉 base64、CSS/JS 內嵌。verify_report.py 會擋下任何 http(s):// 外部資源
demo 的 probe 求值式要寫短 它在 iframe 裡丟出的例外是被吞掉的（刻意設計）。 量測沒出來時，先把 probe 拆簡單再驗

建立新工具時

偵測力要先證明，再相信。 wiring 一開始信心滿滿地回報「全站 0 個死按鈕」——直到拿一個 植入兩顆死按鈕的 fixture 去跑，才發現它把 *.html 也讀進乾草堆， 每顆按鈕都匹配到自己的 id="…"，6/6 全判 wired。 任何掃描型工具，先做一個「答案已知」的 fixture 再說。
