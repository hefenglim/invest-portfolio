外幣期初資金的成本基礎 — 規格 demo v2

這份文件用可操作的 demo 定義規格。文字描述容易各自解讀，demo 不會：你看到的行為就是要實作的行為。

怎麼讀這份文件：每一節先給現況與提案的並排對照，再給一個真的能操作的 demo。規格以 demo 為準，文字只是註解。你在 demo 上點過、認可了，才進入實作。

01問題與目標

v2 · 2026-07-30 會計審查後修訂（owner 認可）

F1 儲存家幣成本金額而非匯率（原設計違反本專案「平均值不得作為權威」的規則）。 F2 明確定義流出的分攤方式為比例法（原設計未定義；直覺的相減法會再生負基數）。 F3 成本基礎不完整時，現金與股票兩條腿一起降級（原設計只降級現金腿， 而股票腿的誤差其實更大）。另補記 N1 外幣出金不認列已實現匯損益、 N2 補填成本會回頭重算歷史顯示值。
期初取得匯率裁決：31.3587（2026-01-05 收盤，owner sign-off 2026-07-30）。

同一個帳戶的同一筆美金，畫面上有兩個數字：各帳戶現金顯示 101,587.90 USD，換匯損益的「外幣現金」卻顯示 1,587.90 USD。兩者都不是算錯——它們是兩套定義；真正的問題是 後者的基數本身少了整整 100,000 USD，而那 100,000 是你當初設定的 期初資金。系統有「期初庫存（股票）」，卻沒有「期初外幣資金」 這個概念，這筆錢在匯率池裡無處安放。

資金視角 — portfolio/cash.py::cash_balances

入金／出金／期初 ± 換匯 ± 買賣收付 ＋ 現金股利。
回答「這個帳戶現在有多少現金」，驅動透支防呆。含 cash_movements。

匯率曝險視角 — forex/pools.py::foreign_cash_balance

換匯 ± 外幣買賣 ＋ 外幣現金股利。
回答「有多少外幣曝險、成本基礎是多少」，驅動換匯損益。 完全不讀 cash_movements。

兩者刻意不同，是有原因的：換匯損益需要成本基礎，而直接匯入的美金沒有台幣取得成本， 硬塞進池子就得捏造一個匯率。pools.py 的模組註解（audit C9） 早就寫下了這個分歧。缺的不是這個判斷，缺的是「期初外幣資金」這個資料結構。

目標

  1. 讓外幣的期初資金／入金可以帶著家幣成本進入匯率池，使 匯率池餘額 = 資金視角餘額，兩個視角可互相對帳。
  2. 沒有成本基礎時不猜、不填 0：金額計入餘額，但依覆蓋率 按比例排除於匯損益基數之外——現金腿與股票腿一併處理，並明確標示缺口。
  3. 警示從症狀偵測（池子為負）改為成因偵測（有外幣資金流 未具成本基礎），消除上表狀態 B 那種靜默失真。

正式站現況：cash_movements 目前 0 筆（唯讀查證）， 所以今天完全不受影響——但你一登錄真實期初資金就會重現。這是預防性修法，不是救火。

02現況 vs 提案：匯率池的重算

現況公式

foreign_cash_balance(transactions, dividends, conversions, …)
三個來源：換匯、外幣買賣、外幣現金股利。
average_acquisition_rate(conversions, …) 只認 home→foreign 的換匯。

提案公式

多一個來源：帶有 acq_home_amount（家幣成本）的外幣資金流 （DEPOSIT／OPENING 為 ＋、WITHDRAW 為 −）。
加權平均同步納入該筆的家幣成本。沒有家幣成本的一律不進加權平均。

F1 · 存的是「家幣成本金額」，不是匯率

期初那筆存的是 3,135,870 TWD（= 100,000 × 31.3587），不是 31.3587。三個理由：

  • data-and-pricing.md 明文「平均成本永不以四捨五入後的值作為權威； 存 total ＋ 數量，讀取時再除」——存匯率正是被禁止的那個模式。
  • fx_conversions 存的是 from_amount／to_amount 兩個金額，匯率是導出的。同一個匯率池的成本基礎，不該一半用金額、一半用匯率。
  • 加權平均的分子要的就是家幣總額——存金額零誤差；存 6 dp 匯率在大額時有殘差， 而且還得額外約定「家幣／外幣」的方向。存金額沒有方向歧義。

登錄介面照樣可以讓你輸入匯率（送出前換算成金額）， 面板顯示的取得匯率一律 家幣成本 ÷ 外幣數 讀取時算。

下面這個實驗不是示意圖：它用真實帳本的 22 列（唯讀取自 /api/cash/statement?account=schwab&ccy=USD），在你的瀏覽器裡以 BigInt 定點運算當場重算兩套公式。頁尾的自我校驗把「現況」模式的每個結果 與 /api/dashboard 的引擎輸出逐項比對——包含 28 位精度的平均取得匯率。

03F2 · 沒有成本基礎時，流出從哪個桶扣

把外幣資金流拆成「有成本基礎」與「無成本基礎」兩個數，只講了一半—— 還必須定義買股票、出金把錢從哪個桶扣。這不是學術問題： 未實現匯損益（現金）= 有基礎的基數 × (spot − avg)，答案完全取決於它。

相減法（直覺，但錯）

有基礎 = 總餘額 − 無基礎取得額
隱含「無基礎的錢最後才花」的 LIFO 假設，與加權平均法矛盾。 餘額一跌破無基礎金額就變負數——反號的假數字回來了，這次修法等於白做。

比例法（採用）

覆蓋率 = 有基礎取得額 ÷ 總取得額
有基礎 = 總餘額 × 覆蓋率
現金是可替代物，加權平均本來就不追蹤批次，流出按比例扣。 任何餘額下都不會為負；全部都有成本時覆蓋率 = 100%，這行不會啟動。

F3 · 股票腿也被污染，不能只降級現金腿

未實現匯損益（股票）= 外幣股票市值 × (spot − avg) 用的是同一個 avg， 而 avg 本身就是從不完整的母體算出來的。實測：股票腿差 +42,359 TWD（+7,178 → +49,537），比現金腿的誤差還大。

因此覆蓋率一律套用在整個外幣曝險上——現金與股票都是同一個可替代資金池支應的：

# 一個比率，兩條腿共用；全部有成本時 covered_ratio = 1，數值與今天相同
covered_ratio        = acq_with / (acq_with + acq_none)
unrealized_fx_cash   = foreign_cash_total  * covered_ratio * (spot - avg_rate)
unrealized_fx_stocks = foreign_stock_value * covered_ratio * (spot - avg_rate)
fx_basis_gap         = foreign_cash_total  * (1 - covered_ratio)

兩處文案一併修掉：(1) 現行提示說「補登入金／換匯紀錄後此提示會自動消失」， 但那筆入金早就登錄了（2026-01-05, 100,000 USD）——補登入金並不會餵進匯率池， 照字面做不會消失。(2) 依 F3，警示必須說明平均取得匯率本身是以不完整的母體計算， 所以受影響的是現金與股票兩條腿，不只是現金。

實作時的修正（2026-07-30，v2 之後）

規格原本寫「警示條件 = fx_basis_gap ≠ 0」。實作時發現這條規則有同一個病灶： fx_basis_gap 是金額（餘額 × 未覆蓋比例），當池子被買光、餘額為 0 時它也是 0—— 警示會消失，可是 covered_ratio 仍然 < 1，股票腿還在被縮放。 那正是「靠症狀判斷會靜默」的翻版。
因此後端改以成因布林值 fx_basis_incomplete（= covered_ratio < 1） 作為警示條件，fx_basis_gap 降為「有金額時順帶說出缺口多少」的細節。 tests/forex/test_fx_pnl.py 的 test_gap_flag_survives_an_EMPTY_pool 釘住這個情形。

附帶的收緊（零成本）：修法後 foreign_cash_total = 資金視角餘額， 而資金視角的出金是硬性擋住的（_withdraw_guard， ack_negative 不能繞過）。因此「池子為負」從預期狀態變成 不該發生的狀態——負值旗標保留為第二個獨立訊號，但意義升級為異常警報。

05登錄時怎麼問、查不到匯率怎麼辦

缺口的成因不是「使用者忘了填」，而是根本沒有欄位可填。 提案在資金管理的登錄表單加一個條件顯示的「取得成本」欄： 只在幣別 ≠ 該帳戶的資金幣別時出現，可用匯率或家幣金額輸入， 預帶當日收盤匯率作參考值，可改、可留白。

這裡有一個實測到的硬限制：正式站的 fx_rates 目前只回溯到 2026-07-01（共 21 天；demo 有 2021 年起的回填）。所以「自動帶入當日匯率」 對早期日期會查不到，手動輸入不是備案，是必要路徑。

06邊界、例外與明確不做的事

必須放行的合法情形（收緊任何規則前先確認這些不被誤殺）

情形正確行為
本幣入金（幣別 = 資金幣別）不出現取得成本欄位，行為與今天完全相同
外幣出金（WITHDRAW）減少匯率池餘額；不認列已實現匯損益（見 N1）
外幣現金股利維持現行處理（已計入池），本次不改
外幣 → 本幣回換維持現行 realized FX 計算，以加權平均取得匯率為成本
取得成本留白計入餘額，依覆蓋率按比例排除於兩條腿的基數之外，並標記缺口
該帳戶完全沒有換匯、只有外幣入金加權平均由入金單獨決定；不得因「沒有 conversions」而回傳 None
完全沒有任何有成本的取得（acq_with = 0） avg_rate 維持 None，兩條腿皆 None；覆蓋率不套用（不得除以零）
完全沒有任何取得（分母為 0）覆蓋率定義為 1，缺口 0（餘額本來就是 0）
股票的期初庫存 opening_inventory不受本次改動影響

必須明文記載的兩個限制

N1 · 外幣出金不認列已實現匯損益

修法後外幣 WITHDRAW 會減少匯率池曝險，但 realized FX 只從 fx_conversions 的 foreign→home 產生。加權平均下這是自洽的 （平均匯率不因處分而變，剩餘曝險 × avg 仍成立），但 若那筆提領實際上換回了本幣，正確登錄方式是一筆換匯紀錄，不是出金。

N2 · 補填成本會回頭重算歷史顯示值

所有報表都從帳本重算（重算模式），不是存檔。所以補上 2026-01-05 的取得成本後， 過去的已實現匯損益也會跟著重算。這是設計意圖 （original_cost 不被覆寫、報表從帳本重建）。 demo 目前 realized_fx = 0（無回換），今天沒有實際影響。

明確不做

  • 不改 XIRR、總報酬、unrealized_total 的定義或數值—— 本次只動換匯損益歸因與 fx_unrealized。
  • 不回溯改寫既有資料列。既有列 acq_home_amount 為 NULL， 匯率池數值與升級前完全相同（差別只在會被新警示標出來）。
  • 不自動猜匯率。查不到當日匯率就留白，不用前後日內插、不用當前 spot 代替。
  • 不引入任何「匯兌收益」加總項——不變式 6：換匯損益是歸因分解，永不加總。
  • 不做 FX 的分批成本（FIFO lots）。維持加權平均，與股票成本法一致。
  • 不加 acq_source（manual／spot）欄位。欄位值是使用者親眼看過才送出的， 多存一欄的效益不足以抵過複雜度——如日後有稽核需求再議。
  • 不動 opening_inventory（股票期初庫存）的任何邏輯。
