## 1. DEF-066（中）— LLM 重試與備援模型實際不可用：缺 `tenacity`，錯誤被原樣寫進運行紀錄

**證據（demo 黑箱，DEF-062 複驗時依開發者指示「立即執行」alert_scan 觸發）**
- alert_scan run #195 派發 → insight:9（持倉提點）run #196～#202。
- #196、#200、#201 皆 `partial`，明細（原文）：`llm_unavailable_mid_run: provider error (haiku-4.5): tenacity import failed please run `pip install tenacity`. ErrorNo module named 'tenacity'`。
- 同批主模型 gemini-2.5-flash-lite 兩次回傳截斷 JSON（invalid_json：EOF while parsing）→ 轉備援 haiku-4.5 → 因上述錯誤失敗。
- 專案虛擬環境 `python -c "import tenacity"` → `ModuleNotFoundError`；`pyproject.toml`／`uv.lock` 無 tenacity。

**根因（讀碼定位，請以你的 traceback 確認）**
- `portfolio_dash/shared/llm.py:323-329`（及 :524-530）以 `num_retries=model.max_retries or 0` 呼叫 `litellm.completion`；模型預設 `max_retries=2`。
- litellm 在 `num_retries>0` 且遇到 provider 例外時走 `completion_with_retries`，該路徑在執行期 `import tenacity`；缺套件時丟出上述訊息，**原本的 provider 錯誤被蓋掉**，重試與備援都失效。
- 運行紀錄明細直接寫入 litellm 例外原文（英文），使用者看不懂。

**規格**
1. 重試真的會重試：把 tenacity 列入相依（或在 `shared/llm.py` 自行實作重試、呼叫 litellm 時 `num_retries=0`），擇一並在 H 欄說明。
2. 主模型失敗後備援模型必須能被實際呼叫；備援也失敗時，明細說明「主模型／備援各自的失敗原因」，用中文句型，provider 原文可放在括號或 fail-log。
3. 同類掃描：所有呼叫 `litellm.completion` 的地方（至少 :323、:524）與所有會把例外字串寫進 `job_runs.detail` 的地方。

**測試**
- 單元：以假 provider 讓第一次呼叫丟 `openai.APIError`、第二次成功 → 斷言有重試且成功；讓主模型永遠失敗、備援成功 → 斷言用了備援。
- 守門：一支測試 `import` 所有 litellm 在執行期會動態 import 的重試相依（至少 tenacity），缺了就失敗（這正是本次漏法：套件缺在「只有出錯才會走到」的路徑）。
- 變異：移除重試實作（或把 tenacity 從 sys.modules 遮蔽）→ 上述測試失敗。

**驗收**：本機或 demo 讓主模型回傳截斷 JSON，run 狀態應為 ok（備援成功）或明細清楚說明兩者各自失敗原因；明細不得再出現 `tenacity import failed`。

## 4. DEF-070（中）— max_shadows 以「該任務累計影子卡張數」計算：第一批不受限、之後的新版本永遠不會有影子批次（G-08）

**證據（本機專用環境，§9）**
- 設定 max_shadows = 2（預設）。2026-09-10 第一批影子一次產生 **9 張**（per_symbol 9 檔），超過上限 2。
- 2026-09-11 再跑：生效卡 9 張、影子 0 張（假模型收到 0 次帶校正層的呼叫）——「已存影子卡 9 ≥ 2」即跳過。
- 2026-09-21 v2 晉升生效後，新產生 v3（最新版 ≠ 生效版 → v3 應成為影子）；再跑任務：生效卡 9 張（套 v2），**v3 影子 0 張**；診斷 G7 仍為「有未套用的校正版本」。影子卡永遠不會減少，因此**第一次晉升之後，這個任務的任何新版本都不可能再被評估或晉升**。
- 推論（未另建情境）：portfolio 範圍任務每批 1 張，累計 2 張即停止，而影子評估批次數最小值是 3，**永遠達不到晉升門檻**。

**根因**：`portfolio_dash/api/insight_service.py:403-407` `_shadow_card_count` 計算 `insights WHERE insight_type_id = ? AND is_shadow = 1` 的**全部歷史**；`:436` 以 `>= max_shadows` 跳過。

**規格（owner ⑧ 裁定 A）**：上限計的是「同時處於影子期的**任務數**」。影子期＝該任務的最新校正版本 ≠ 生效版，且該影子版本尚未累積到 shadow_batches 筆評分（或已達門檻但尚未完成晉升判定）。新任務要進入影子期時，若已有 max_shadows 個任務在影子期 → **排隊**（本批不產影子，下批再試），並在運行紀錄或診斷中說明「影子排隊中（目前 N／上限 M）」。同一任務在影子期內每一批都要產影子卡（per_symbol 一批 N 張屬於同一個任務名額）。晉升、封存影子版本或生效版追上最新版後，該任務離開影子期、釋出名額；舊影子卡不得再佔用名額。

**測試**：情境測試——(a) 晉升後產生新版本 → 下一次執行有新版影子卡；(b) 兩個任務同時有影子、上限 1 → 第二個排隊、第一個結束後輪到它；(c) portfolio 任務可累積到 shadow_batches 次並晉升。變異：改回全歷史計數 → (a)(c) 失敗。
