## 1. DEF-056（部分通過 → 複驗未過）— 畫面上的「現金收支明細」未標示未來列，與「目前餘額」互相矛盾

**證據（demo 黑箱，測畢已刪除）**
- 資金管理 › 券商費用 100 TWD，日期 2026-10-20（#52）。
- 六段 JSON 與寫入前逐字相同 ✓；出金入金列表顯示「2026-10-20　未來日期：2026-10-20 起計入」✓；⎙ 匯出報告有「以下 1 筆為未來日期（2026-09-25 之後），不計入目前餘額；其餘額欄為投影」✓。
- ✗ 帳戶現金 › 台灣券商 的**畫面**「現金收支明細」：表頭「台灣券商・TWD　目前餘額 6,067,595 TWD」，第一列卻是「2026-10-20　券商費用　−100　餘額 6,067,495」，沒有任何未來標示或投影說明。
- `GET /api/cash/statement` 該列已帶 `future: true`，是前端沒讀。

**根因**
- `web/cash.js:402-420` 明細列渲染只用 `f.date(r.date)`，沒讀 `r.future`；同檔 `dateCell(dateIso, countsFrom)`（:44）只用在出金入金與換匯列表。
- `portfolio_dash/export/cash_statement.py:215` 的 docstring 寫「The web statement … flags the rows past it」，但畫面實際沒做。這是 DEF-056 同類掃描漏掉的一個面。

**規格**
1. 明細中第一筆未來列之前加一條分隔列，文字與列印報告一致：「以下 N 筆為未來日期（YYYY-MM-DD 之後），不計入目前餘額；其餘額欄為投影」。
2. 每筆未來列的日期欄加「未來日期：YYYY-MM-DD 起計入」徽章（沿用 `dateCell` 或 `.ledger-future`）。
3. 餘額欄對未來列加視覺區隔（例如斜體或 `—投影` 標示），不得讓人把它讀成目前餘額。
4. 表頭「目前餘額」維持目前數字（不含未來列）。
5. 合併幣別檢視（`combined`）同樣適用。

**同類掃描**：列出所有以 `/api/cash/statement`、`counts_from` 或 `future` 渲染的畫面與列印面，逐一確認都有標示；owner ③ 已裁定個股抽屜交易明細不列未來列，掃描結果裡註明即可。

**測試**
- e2e：寫一筆未來券商費用 → 開明細 → 斷言分隔列文字、該列徽章存在，且表頭目前餘額不含這筆。
- 變異：`cash.js` 不讀 `r.future` → 上述 e2e 失敗。

## 2. DEF-062（新開・低）— 新增洞察任務精靈的「監聽規則」有 8 個勾選框直接顯示規則 id

**證據（demo 黑箱，1ee7771）**
- 洞察管線 › ＋新增洞察任務 → 觸發選「預警觸發」→ 監聽規則 15 個勾選框中：
  - 7 個是中文：單一標的集中度、產業集中度、價格過期/缺價、匯率漂移、即將除息、AI 額度偏低、AI 校準誤差。
  - **8 個直接顯示 id**：`missing_price`、`drawdown_from_peak`、`vol_spike`、`rebalance_drift`、`consensus_change`、`portfolio_drawdown`、`currency_weight`、`target_cross`。
- 系統設定 › 預警規則把這 15 條都顯示成中文（例：高點回撤、波動突升、配置漂移、分析師共識轉弱、組合整體回撤、幣別集中度、目標價穿越、缺價）。

**根因**
- `web/pipeline-wizard.js:23-29` 的 `RULE_LABELS` 只列 7 條，`ruleLabel(id)` 查不到就回傳 id。
- 同一組名稱另有兩份：`web/settings-alerts.js:25-70`（15 條）與 `portfolio_dash/ops/notify.py:86` 附近（後端）。三份文字也不一致，例如 `stale_price` 是「價格過期/缺價」vs「價格過期」，`exdiv_upcoming` 是「即將除息」vs「即將除息提醒」。
- DEF-053 的同類掃描只涵蓋「範圍」識別字，沒涵蓋規則 id。

**規格**
1. 規則名稱只保留**一份**，建議放在後端（`ops/notify.py` 的表或 `strategy/rules_config.py`），`GET /api/alert-rules` 每條帶 `name`。精靈、設定頁、抽屜與通知都讀 `name`。
2. 前端不再各自維護對照表；若保留後備，查不到時顯示「未命名規則」並在 console 留警告，**不得**顯示 id。
3. 統一用語，以設定 › 預警規則現行名稱為準。

**同類掃描**：grep 所有渲染規則 id 的地方，例如精靈、任務抽屜「觸發」節、卡片「觸發預警」晶片、通知中心、預警鈴鐺面板、排程 detail 字串中的規則清單。附數字：共 N／修 M／白名單 K。

**測試**
- 契約：後端每個規則 id 都有非空中文 `name`（以規則註冊表為母集合，新增規則沒給名稱就失敗）。
- e2e：精靈 15 個勾選框的文字皆不符合 `/[a-z]+_[a-z_]+/`。
- 變異：刪掉其中一條名稱 → 契約測試失敗；精靈改回讀本地表 → e2e 失敗。

## 3. DEF-063（owner ④ 裁定・資料殘留）— 清理 demo 上的孤兒起始價

**背景**：R4 起 `write_seed_price` 只寫空白日期，刪除只收回 `child_seed_json` 記錄的那一列（DEF-040 已結案）。所以 R2／R3 期間留下的孤兒起始價不會再被覆蓋或刪除，但畫面上沒有地方能移除。另外，R3 版本曾把正式報價蓋掉（本機重現）；demo 上若有同類情況，歷史回補可以取回。

**孤兒定義**（全部成立才算）
- `prices.source = SEED_SOURCE`（`"manual"`），且 `fetched_at` 等於 `as_of_date` 00:00（簽章完整）；
- 沒有任何 `corporate_actions` 的 `child_seed_json` 指向這個 `(instrument, as_of_date)`；
- 也沒有任何舊格式（`child_seed_json` 為 NULL）的 SPINOFF 以 `to_symbol = instrument` 且 `date = as_of_date` 擁有它（R3 的簽章規則）。

**規格**：新增 `scripts/clean_orphan_seed_prices.py`，比照 `scripts/clean_rebate_snapshots.py` 與 `delete_insight_cards.py` 的慣例：
1. 預設試跑：列出每一列的 symbol、日期、close、fetched_at，以及判定理由；不寫入。
2. `--apply --reason "…"`：先備份資料庫（檔名含時間），再逐列刪除，每列寫 `ledger_audit`（source `script`，留原始內容）與 `action_log` 一筆摘要。
3. `--backfill`（選用）：對受影響的標的跑一次歷史回補，取回正式報價；回補寫入數量印在結果裡。
4. 重跑為 no-op（試跑結果為 0 列）。
5. 不得碰 `child_seed_json` 記錄仍擁有的種子列，也不得碰非 `manual` 來源的列。

**測試**：`tests/scripts/test_clean_orphan_seed_prices.py` 覆蓋以下情況：孤兒被刪；仍被擁有的種子不動（新舊兩種擁有方式都要）；正式報價不動；簽章不完整（`fetched_at` 不是 00:00）不動；試跑不寫入；重跑 no-op；稽核列內容完整。
- 變異：擁有判定只看 `child_seed_json`（忽略舊格式簽章規則）→ 至少一則失敗。

**demo 執行**：交付時在 L 欄附試跑清單與 `--apply` 結果、action_log 編號、備份檔名。驗證者下一輪會用 API 與標的抽屜價格序列核對。

## 4. DEF-064（owner ⑦ 裁定・低）— 報價類抓取宇宙排除已封存標的

**證據（讀碼，1ee7771）**
- `portfolio_dash/pricing/ingest.py:52-57` 的 `tw_universe` 是 `SELECT symbol FROM instruments WHERE market = 'TW'`；`:60-73` 的 `all_universe` 是 `SELECT … FROM instruments`。兩者都沒有 `archived` 條件。
- 使用者：`ingest_chips`（:126）、`ingest_valuation`（:144）、`ingest_fundamentals`（:156）、`ingest_consensus`（:238）、`ingest_fundamentals_union`（:288），也就是開發者交接所說的 5 個排程。
- 對照：`portfolio_dash/scheduler/jobs.py:1292` 的報價宇宙已經是 `WHERE COALESCE(archived,0)=0`；DEF-059 的洞察宇宙也已排除封存。

**規格**
1. 兩個宇宙都排除 `archived = 1` 的標的。
2. 持倉中的標的永遠在內（booking 已保證「持有 ⇒ 未封存」，但仍要有測試釘住）。
3. 規則與 DEF-059、`jobs.py:1292` 用同一個判定，避免第四份定義。建議抽一個 `active_instruments_sql()`，或在 `pricing/` 內放共用 helper。
4. 封存後再還原的標的，下一次排程自然回到宇宙；缺口由既有的 `gap_backfill` 處理，不需額外動作。

**同類掃描**：grep `FROM instruments` 的所有讀取點，逐一標註「應含封存／應排除封存」並附理由（例如帳本匯出、歷史查詢應含封存）。附數字：共 N／修 M／白名單 K。

**測試**：兩個宇宙在有封存標的時各少一檔；持倉標的永不被排除；5 個 ingest 函式收到的宇宙不含封存標的（monkeypatch fetch 取得實際送出的清單）。
- 變異：拿掉 `archived` 條件 → 失敗。

## 5. DEF-065（新開・低）— `GET /api/ui-prefs` 間歇性 500，e2e 全套不穩定

**證據（驗證者在 repo 1ee7771 本機）**

| 次 | 結果 | 失敗項 |
| --- | --- | --- |
| 1 | 287 passed／1 failed | `test_def057_global_prompt_versions_flow` |
| 2 | 287 passed／2 failed | `test_def033_prompt_versions_flow`、驗證者加了回應記錄的 def057 副本 |
| 3 | 289 passed | —（以 `PD_E2E_NETLOG` 保留 183 份伺服器記錄，當次沒發生） |

- 每次失敗的都只有最後的 `assert errors == []`：console 出現「Failed to load resource: … status of 500」。功能斷言全部通過。
- 副本以 `page.on("response")` 記到的是 `500 GET /api/ui-prefs {"error":{"code":"internal_error","message":"系統發生未預期的錯誤，請稍後再試"}}`。這是應用程式自己的錯誤處理器回的，不是測試框架造成。
- 單獨重跑 18 次、在另一個 pytest 佔 CPU 時連跑 4 輪、全新伺服器 12 次 ×54 個並發 GET，全部沒重現。

**讀碼疑點（待開發者以 traceback 確認）**
- `shared/ui_prefs.py:55` 的 `get_ui_prefs` 每次都呼叫 `ensure_ui_prefs_seeded` → `shared/config_store.py:22` 的 `ensure_seeded`。每個 GET 都執行 `CREATE TABLE IF NOT EXISTS`、`PRAGMA table_info`，首次還會 `INSERT`＋`commit`。讀取路徑帶寫入／建表，遇到其他連線持有寫鎖時可能拋 `sqlite3.OperationalError`，最後變成 500。
- 開發者回報「e2e 288 全過」，但驗證者 3 次全套只有 1 次全綠，閘門本身不可靠。

**規格**
1. 用 `PD_E2E_NETLOG=<dir>` 連跑全套，直到抓到 traceback，把根因寫到檔案:行。
2. GET 路徑不得建表或寫入：`ensure_seeded` 移到啟動時（`create_app` 或 migration），或 GET 改成只讀、沒有列時回預設值。
3. 同類掃描：所有在 GET handler 內呼叫 `ensure_seeded`／`ensure_table`／`CREATE TABLE` 的路由，附數字。
4. 若根因不是鎖（例如 schema 遷移競態），照實修並說明。

**測試**
- 契約：GET `/api/ui-prefs`（與同類 GET）在資料庫被另一條連線持有寫鎖時仍回 200 預設值／既有值，不回 500。
- 變異：把 `ensure_seeded` 放回 GET 路徑 → 契約測試失敗。
- 交付時附 e2e 全套**連跑 3 次**的結果。
