### 🔴 高（H）

#### H1 — 再平衡試算：目標合計剛好 100.00% 仍顯示「⚠ 目標合計超過 100%」

- **現象**：在「再平衡試算」把 3008 從 58.5 改成 58.4，footer 顯示「目標合計 **100.00%**」，但下方仍掛著紅字「⚠ 目標合計超過 100% — 請下調部分標的」。
- **重現步驟**：儀表板 → 持倉明細 → `⚖ 再平衡試算` → 任一標的目標值 −0.1，使合計為 100.0。
- **測量證據**（實際攔截的 request body）：
  ```json
  {"targets":{"1155":"0.006999999999999999","2317":"0.004","2330":"0.179",
   "2603":"0.01","2884":"0","3008":"0.584","5225":"0.006999999999999999",
   "8299":"0.111","AAPL":"0.026000000000000002","MSFT":"0.024","0056":"0.008",
   "TSLA":"0.036000000000000004","NVDA":"0.004"}}
  ```
  回應 `summary.over_allocated: true`。
- **根因（已在前後端兩側確認，非推測）**：
  1. 前端 `web/rebalance.js:220` — `state[sym] = Math.max(0, Number(inp.value) / 100 || 0)`，以 **JS float** 計算比例，`0.7/100` 序列化成 `"0.006999999999999999"`、`3.6/100` 成 `"0.036000000000000004"`。
  2. 後端 `portfolio_dash/strategy/rebalance.py:198` — `over_allocated = submitted_sum > _ONE`，**完全沒有容差**。
  3. 這些 float 殘渣以 Decimal 相加後為 `1.000000000000000004 > 1`，於是旗標為真。前端的保險絲 `sumTarget > 1.0001`（`rebalance.js:293`）反而正確判為 false，所以畫面上寫著 100.00% 卻同時報錯。
- **建議**：前端改送定點字串（`(pct/100).toFixed(6)`），**並且**後端加容差（`> Decimal("1.0001")`）。兩邊都補才不會下次從另一個方向重演。同時這也是 `CLAUDE.md` 不變量 3「金額不走 float」的精神漏洞。

> **修復狀態：✅ 已修復**
> 修法：前後端各補一邊，兩邊都補。`web/rebalance.js`：目標權重改以「整數・千分之一（0.1%）」為狀態，送出字串由整數直接拼出（不再 `String(float)`），前端 Σ>100% 檢查改用整數相加；`strategy/rebalance.py`：`over_allocated = Σ > 1 + 0.0001`（容差，並註明 1 dp 欄位最小超額為 0.001，容差永遠遮不住真超額）。測試：用報告攔截到的那組 body（Σ=1.000000000000000004）斷言 `over_allocated is False`，100.1% 仍為 True；另有靜態契約測試禁止 `Number(inp.value)/100` 與 `1.0001` 回流。

### 🟠 中（M）

#### M1 — 三組匯率彼此不三角一致，換匯會讓報告幣別淨值憑空變動

- **現象**：`USD/TWD`、`USD/MYR`、`MYR/TWD` 三個報價各自獨立儲存，彼此不滿足 no-arbitrage。
- **測量證據（重新整理報價後、三組匯率皆為 2026-09-15 且 `stale:false`，非過期造成）**：

  | 幣對 | 系統值 |
  | --- | --- |
  | USD/TWD | 31.834999 |
  | MYR/TWD | 7.803300 |
  | USD/MYR | 4.082500 |
  | **推導 USD/TWD**（4.0825 × 7.8033） | **31.856972** |
  | **落差** | **+0.0690%** |

- **可觀察後果**：實測在 Moomoo MY 帳戶用即期價把 4,000 MYR 換成 983.28 USD，`/api/cash.reporting_total` 從 `25,404,962.183375760` 變成 `25,404,921.306279040`，**憑空少了 40.88 TWD**。刪除該筆換匯後金額逐位元還原，證明差額完全來自匯率換算路徑，不是帳務錯誤。
- **影響**：馬股／美股部位的報告幣別數字會因換算路徑不同而有 0.05–0.13% 的差異；換匯這個本應「報告幣別價值中性」的動作會產生幻影損益。
- **建議**：指定一個 base（例如 USD），另兩組由 cross rate 推導；或在 `pricing/` 層加一道三角一致性檢核並在「資料新鮮度」標示落差。

> **修復狀態：✅ 已修復（檢核＋揭露）／❓ 待你決策（改資料源）**
> 修法：後端 `portfolio/dashboard.py` 在組 `freshness` 時，對已儲存的三組匯率做三角檢核：`implied = USD/MYR × MYR/TWD`、`direct = USD/TWD`、`gap_pct`，`|gap| ≤ 0.05%` 才算 `ok`，以 `freshness.fx_triangulation[]` 回傳（Decimal 字串，匯率本身不動）。前端 `web/app.js` 在「資料新鮮度」面板以琥珀色註記落差與原因。用報告的實測值做單元測試（推得 31.856972、落差 0.0690%、`ok=False`）。**要不要指定 base 幣別、把另兩組改成 cross rate 推導**會改動報告幣別數字，留給你決策（見文末問題 1，含 0.05% 門檻是否合適）。附帶：spec-17 golden payload 因新增欄位重新基線（+14／−1 行，只有這兩個新鍵），其合成匯率本身三角落差 −3.75%，golden 因此記為 `ok:false`，是誠實的回歸錨點。

> **修復狀態：✅ 已修復**
> 修法：根因與報告的推測不同：不是文案設計，而是**競態**——使用者在試算請求還在飛時手動填買入金額，`runEstimate` 的 `!estPristine` 早退正確地丟掉答案，但沒有一起收回「試算中…」。`web/cash.js::markBuyEdited` 現在在 input 事件當下同步改寫說明為「已手動指定買入金額 — 按「重新試算」可依即期匯率回填」。既有的 pristine 不變量（e2e）不受影響。

### 金額與成本計算 — 93 項恆等式全數通過

以 `/api/dashboard` 原始 Decimal 字串獨立重算：

- `已實現 + 未實現 = 資產損益` ✅
- `含匯兌總損益 = 資產損益 + 本金匯率效果 + 交易與融資成本` ✅
- `Σ 各帳戶市值 = Σ 各市場市值 = 總市值` ✅
