## 1. DEF-040（複驗未過）— 分拆起始價覆蓋既有正式報價，刪除後原報價永久遺失

**證據**
- 黑箱正常路徑通過：2884 → 2882 分拆，日期 2026-09-20（2882 當天沒有報價），起始價 30。刪除後 2882 價格序列的 117 點與登錄前逐字相同。
- 本機 4655845 以 TestClient 走真實路由抽驗「子公司當天已有正式報價」的情況。流程：CHLD 在 2026-03-16 先有一筆 yfinance 48.70 → 登錄分拆，起始價填 50.00 → 刪除。
  - 存檔後，該列變成 `{close 50.00, source manual}`（原報價被覆蓋）。
  - 列表承諾 `restorable: true`，刪除回 `restored: true`。
  - 刪除後該日已沒有任何價格列，48.70 永久遺失。
- 定位：`portfolio_dash/pricing/seed.py` 的 `write_seed_price` 經 `upsert_prices` 的 `ON CONFLICT` 覆蓋同日正式報價，而且沒有保存被覆蓋的原值。`remove_seed_price` 只看「現在是不是種子」。
- 違反手冊 v3.1 D-10：「子公司起始價全部回到行動前的狀態，逐位元比對」。

**規格（建議 A）**
1. 寫入前，如果 `(to_symbol, date)` 已有 `source ≠ SEED_SOURCE` 的價格列，**不寫入起始價**：
   - 回應 `child_priced: null`，另帶 `child_price_skipped: {symbol, date, existing_close, source, reason}`。
   - 表單與 toast 說明「2882 在 2026-09-20 已有正式報價 112.0（來源 yfinance），起始價未寫入」。
2. 已有種子列（同一天、另一筆分拆寫的）時維持現有 `still_used` 邏輯。
3. 刪除時的判定不變；但因為第 1 點，刪除不可能再刪到正式報價。

**替代 B**：寫入時把被覆蓋的原列存進 `corporate_actions.seed_replaced_json`，刪除時原樣放回。複雜度較高，不建議。

**實作計畫**
- `pricing/seed.py`：新增 `existing_provider_price(conn, symbol, on)`。`write_seed_price` 改為回傳 `SeedWriteResult(written: bool, skipped_reason: str | None, existing: …)`。
- `api/routers/ledgers.py`：`_seed_child_price` 依結果回傳 `child_priced`／`child_price_skipped`。前端 `corp-action-form.js` 顯示 toast。
- 同類掃描：所有呼叫 `upsert_prices` 且 `source` 為人工的寫入點（grep `upsert_prices(` 與 `source=`）。

**驗收**
- 新增契約測試：當天先有 provider 報價 → 存檔＋刪除 → 該列 `close`／`source`／`fetched_at` 逐字相同，且回應帶 `child_price_skipped`。驗證者的探測測試附在附錄 A，可直接改寫成正式測試。
- 變異測試：拿掉「已有正式報價就跳過」→ 上述測試失敗。
- 黑箱：驗證者會在 demo 以「子公司當天已有報價」重放。修好後才不會銷毀 demo 報價。

## 2. DEF-049（新開・中）— 匯入批次「復原」繞過重播防護：之後的賣出變成賣超，不確認、不留稽核

**黑箱證據（demo，已還原）**

| 步驟 | 操作 | 結果 |
| --- | --- | --- |
| 1 | CSV 匯入 2884 買 100（2026-09-23，批次 15） | 持股 100 → 200 |
| 2 | 手動賣出 2884 150 股（2026-09-24，#108） | 草稿「持股 200 → 50」，寫入成功 |
| 3 | 按批次 15 的「復原」 | 框內只寫「將刪除這批匯入寫進帳本的 1 筆交易紀錄…」，**沒有任何賣超警示**；`DELETE /api/import/batches/15` 200 `{"deleted":1}` |
| 4 | 看儀表板 | 2884 `shares -50`、`adjusted_cost_total 0`（成本基礎被捨棄）、XIRR `null`、「帳本中有賣超部位待釐清」 |
| 對照 | 用交易帳本「刪除」同一筆買進（#109） | `DELETE /api/ledgers/transactions/109` **422 oversell**，並跳出「賣超確認」框 |

- 根因：`input_center.py:1675 import_batch_delete` → `provenance.delete_batch`（provenance.py:294–297）對 `transactions／dividends／fx／cash` 直接下 `DELETE FROM {table} WHERE import_batch_id=?`。
  - 沒有經過 `ledgers._replay_guard`（孤兒／賣超判定）。
  - 沒有經過 `store._write_audit`（逐筆刪除會寫 `ledger_audit`，批次刪除不寫）。
- 公司行動已走 `_delete_actions`（I-3），但其他四類沒有。

**規格**
1. **重播防護與逐筆刪除一致**：`DELETE /api/import/batches/{id}` 在刪除前以「目前帳本扣掉本批次所有列」組成 would-be 帳本，呼叫與帳本刪除**同一個** `_replay_block`：
   - 造成孤兒（股利／期初失去持倉）→ 422 `orphan_correction`（硬擋，不能 ack）。
   - 造成新賣超或加重賣超 → 422 `oversell`，訊息逐筆點名，例如「此復原將使 2026-09-24 的 2884 賣出 150 股超過當日持股 100 股，確認後這個部位的成本基礎會被捨棄（待釐清）」。帶 `ack_oversell=true`（query 或 body）才放行。
   - 既有、與本批次無關的賣超不影響（沿用 `_replay_block` 的 pre/post 比較）。
2. **稽核一致**：本批次刪除的每一列在**同一交易內**寫 `ledger_audit`（`action='delete'`，`before_json`＝整列，附 `import_batch_id` 與「批次復原」來源）。另寫一筆 `action_log`：批次 id、筆數、是否 ack 賣超。
3. **前端**：`broker-import.js` 的 `undoBatch` 收到 422 oversell 時，顯示與帳本刪除同一款的「賣超確認」框，逐筆列出受影響的賣出與成本基礎後果。確認後帶 ack 重送，取消則不動。收到 `orphan_correction` 顯示原因、不提供強制。
4. 單列表單寫入的批次（來源「手動輸入」）同樣適用。

**實作計畫**
- 把 `_replay_block` 需要的 would-be 組裝抽成共用函式（例如 `ledgers.would_be_without(conn, *, batch_id)`，回傳四類 would-be 清單），供批次復原呼叫。避免 `input_center` 反向 import `ledgers` 私有函式：可把 `_replay_block`／`_replay_guard` 移到 `data_ingestion` 或 `api/replay_guard.py`。
- `provenance.delete_batch`：非公司行動的四類改為逐列經 `store` 的刪除函式（會寫稽核），或在同一交易先把要刪的列 `SELECT` 出來寫 `ledger_audit` 再 `DELETE`。
- 同類掃描：全 repo 搜尋 `DELETE FROM (transactions|dividends|fx_conversions|cash_movements|openings)`，所有不經 `store.delete_*` 的點（腳本、批次、帳戶刪除、標的永久移除）逐一列出處理方式；寫成守門測試，禁止新增繞道。

**驗收**
- 契約測試：
  - 批次買進＋手動賣出使復原造成賣超 → 422 oversell（訊息含日期、代號、股數）。
  - 帶 ack → 200，`ledger_audit` 多一筆 delete，`action_log` 有紀錄。
  - 批次買進＋只靠它支撐的股利 → 422 `orphan_correction`。
  - 與本批次無關的既有賣超 → 不擋。
- 變異測試：拿掉 guard → 422 測試失敗；拿掉稽核 → 稽核測試失敗。
- e2e：CSV 匯入 → 手動賣出 → 復原 → 出現賣超確認框 → 取消後帳本列數不變。
- 黑箱：驗證者會重放上表步驟 1～4。
