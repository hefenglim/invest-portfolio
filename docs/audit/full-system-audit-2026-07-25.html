03高風險缺口

會讓使用者看到錯誤數字或做出錯誤判斷的問題。兩項皆已在實測站重現。

HIGH 個股抽屜「未實現損益」的百分比在已回本標的上符號反轉 · H1 · web/detail.js:443-446›

症狀

當某標的的累計現金股利超過原始成本（台股高股息長抱的常見終局），抽屜的「未實現損益」會在一個 正數獲利旁邊印出一個大幅負數的百分比。

實測重現

標的 0056（tw_broker）· 原始總成本 190,027 · 累計配息 206,000 · 市值 207,500 adjusted_cost_total = 190,027 − 206,000 = −15,973 ← 依 domain-ledger.md 合法，「may be ≤ 0，never floored」 adjusted_avg = −3.1946 unrealized_pnl = (41.5 − (−3.1946)) × 5,000 = +223,473 抽屜 DOM 實際渲染： 股數 5,000 未實現損益 +223,473 −1399.07% ← 正獲利 / 負百分比 回本進度 108.41%

根因

// web/detail.js:443-446 — 前端自行推導的比率
const adjTotalN = Number(h.adjusted_cost_total);
const pnlPct = (h.unrealized_pnl != null && adjTotalN)
  ? f.signedPct(Number(h.unrealized_pnl) / adjTotalN) : null;
  • adjTotalN 只擋 0（falsy），不擋負數；負分母直接讓比率翻號。
  • 更根本地：這違反鎖定的不變量「前端永不計算金額或報酬；所有數字由 API 以 Decimal 字串提供」。 這是上一輪 F10（匯損益前端浮點加總）修掉的同一類問題的第三次復發。
  • 分母選擇也與 domain-ledger.md 不一致：規則定義「總報酬率 = 總報酬 / 原始投入成本」， 此處卻用 adjusted。同一頁的「回本進度」用 original，兩個百分比基準不同卻無標示。

建議修法

# portfolio_dash/portfolio/dashboard_models.py — HoldingRow 增欄
unrealized_pct: Decimal | None = None   # unrealized_pnl / original_cost_total（原幣，與報酬率定義同基準）

# dashboard.py 第 8 段組列時（Decimal，None 安全）
pct = (h.unrealized_pnl / h.original_cost_total
       if h.unrealized_pnl is not None and h.original_cost_total != _ZERO else None)

// web/detail.js — 只顯示，不計算
- const pnlPct = ... Number(h.unrealized_pnl) / adjTotalN ...
+ const pnlPct = h.unrealized_pct == null ? null : f.signedPct(h.unrealized_pct);

同時建議在 adjusted_avg < 0 時於「調整均價」旁加一枚已回本標記—— 目前直接顯示 -3.19 元的均價，沒有任何說明。

回歸測試建議：新增一個 hermetic 案例（配息 > 成本），斷言 unrealized_pct 為正； 並在 scripts/stress_audit 加一個「高配息回本」場景 op，讓 oracle 永久看守。

HIGH 清倉後才入帳的現金股利，從「總報酬」中無聲消失 · H2 · portfolio/cost_basis.py:143-150›

症狀

台股除息在前、發放在後；若在這段期間把部位賣光，該筆現金股利仍會入帳。 系統的「股利總覽」有計入、XIRR 現金流有計入， 但 KPI「總報酬 / 已實現 / 未實現」完全沒有計入——同一筆錢，三個指標三種答案。

實測重現

起點：0056 持有 5,000 股 ① 賣出 5,000 股 @ 41.5（手續費 29 / 稅 207） realized_total = 23,237 total_return = 3,941,081 股利總覽 = 206,000 ② 再補一筆「賣出日之後」的現金股利 7,500 TWD realized_total = 23,237 total_return = 3,941,081 ← 完全沒動 股利總覽 = 213,500 ← 這裡有加 Δ total_return = 0.0000（若計入應為 +7,500）

根因

# cost_basis.build_book — 股利事件（第 121-133 行）
if ev.type in CASH_DIVIDEND_TYPES:
    existing.adjusted_total -= ev.net      # 部位已 0 股，仍照扣 → adjusted_total 變 −7,500

# …但組 holdings 時（第 143-146 行）
for (account_id, symbol), pos in positions.items():
    if pos.shares == _ZERO:
        continue                            # ← 這筆 −7,500 隨著 0 股部位一起被丟棄

已實現損益在賣出當下就結算完畢，之後的沖減無處可去；而 dividend_summary（第 6 段） 是獨立遍歷所有股利列的，所以它看得到。兩條路徑對「一筆股利算不算數」的定義不一致。

影響

  • 低估總報酬，金額等於「所有清倉後入帳的股利淨額」總和——長期存股帳本上並不罕見。
  • 總報酬率、各幣別報酬折分同步低估（分子少了，分母 gross_invested 不變）。
  • 使用者若拿「股利總覽」和「總報酬」互相驗算，會發現對不起來且無從解釋。

建議修法

# cost_basis.build_book：0 股部位的現金股利 → 直接記為一筆已實現
if ev.type in CASH_DIVIDEND_TYPES:
    if existing.shares == _ZERO:
        # 清倉後入帳的股利：成本沖減已無標的，改記為已實現收益（一次，不重複計）
        realized_rows.append(RealizedRow(
            account_id=ev.account_id, symbol=ev.symbol, quote_ccy=quote_ccy(ev.symbol),
            sell_date=ev.date, shares_sold=_ZERO, proceeds_net=ev.net,
            original_cost_removed=_ZERO, adjusted_cost_removed=_ZERO, realized=ev.net))
    else:
        existing.adjusted_total -= ev.net

這一改動動到 money-of-record，依 ship-version 第 9 條必須： 同步擴充 scripts/stress_audit/oracle.py + 一個 run_phase1.py 場景 op、 更新 docs/accounting-formula-manual.md（含中英兩版）、重跑 phase 1 至 fail=0。 建議先請 owner 對「記為已實現」vs「不入報酬僅記現金」做一次裁決並寫進 CHANGELOG。

MED 換匯損益建立在可能為負的外幣現金池上，且介面完全無提示 · M4 · forex/pools.py · web/app.js:688›

機制

未實現匯損益 = (外幣股票市值 + 外幣現金) × (即期 − 加權取得匯率)。 其中「外幣現金」是由換匯 + 外幣交易 + 外幣股利反推出來的， 不含直接匯入的外幣入金。所以只要出入金沒有完整登錄，這個池就會是負的。

實測站 /api/dashboard → fx.by_account.schwab avg_rate 32 current_spot 32.5 foreign_stock_value 12,120 USD foreign_cash −2,675 USD unrealized_fx_stocks +6,060.0 unrealized_fx_cash −1,337.5 unrealized_fx_total 4,722.5 → 直接進 KPI「換匯損益・未實現」 同一份資料的 /api/cash：五個資金池全部為負（tw_broker TWD −1,384,198…）， negative_pools 已被資金管理頁警示，但儀表板的匯損益卡片沒有任何交叉提示。

兩處對「現金」的定義本來就不同（forex/pools.py 的 docstring 有明確說明，設計是自洽的）， 問題在於使用者看不到這個前提：一個看起來精確到小數的匯損益數字， 其實對「入金有沒有補登」高度敏感。

建議

  • 當 foreign_cash < 0 時，於 FX 卡片該列加警示徽章： 「現金池為負（出入金可能未補登），匯損益歸因可能失真」。
  • 後端在 AccountFXResult 增一個 cash_basis_incomplete: bool， 由後端判定，前端只顯示（維持不變量）。
  • 另一面向：本項也連帶影響公開 demo 的觀感——見 L6。

LOW 折讓款待確認清單沒有時間窗，歷史匯入會一次湧現 · L4 · api/rebates.py:detect()›

detect() 是 compute-on-read、無狀態（只有 skip 表），會回傳所有 未確認且未略過的月份。這個設計本身很好（自癒、不寫入），但一旦匯入數年台股歷史， 收件匣會瞬間出現數十筆待確認，逐月「略過」才能清空。

建議：加一個「折讓款起算月份」設定（預設＝首次啟用當月）， 早於該月份的一律不顯示；或只保留最近 N 個月並提供「顯示更早」。

LOW 顯示層的四捨五入走浮點，理論上可能與後端 Decimal 差 1 分 · L5 · web/format.js:12-25› 
function num(v, dp){ return Number(v).toLocaleString('en-US', {…}); }

金額本身確實是後端來的 Decimal 字串（passthrough 保證成立），但顯示的取位 是浮點四捨五入。當一個未量化值的第三位小數恰為 5 時（如 0.145）， JS 會得到 0.14、後端 ROUND_HALF_UP 會得到 0.15。

目前費稅等值在後端已量化，實務衝擊接近零；列在此僅為完整性。若要根治， 由後端額外提供已量化的顯示字串（或前端改用整數分運算）即可。

LOW demo 種子資料缺匯率歷史與入金，導致公開 demo 站的旗艦指標全部無法顯示 · L6 · scripts/seed_demo.py›
以 seed_demo.py 資料實測： xirr = null xirr_unavailable_reason = "no FX rate stored on or before 2026-01-15 for USD/TWD" trend.available = false（"missing FX history for a ledger flow date"） 現金池 = 五個池全部為負（種子只記交易，未記入金）

降級行為本身完全正確（誠實標示原因、不捏造）， 但這代表公開 demo 的訪客看到的是：「年化報酬 (XIRR)」空的、資產趨勢圖空的、所有帳戶現金為負—— 恰好是最想展示的三樣東西。

建議：在種子中補上 (a) 每筆交易日前的 USD/TWD、MYR/TWD 匯率歷史列， (b) 對應的入金 cash_movements（或 opening 期初資金）， 讓 demo 呈現完整的 XIRR、趨勢曲線與正的資金池。
