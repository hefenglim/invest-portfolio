## 1. 你拿到之後的第一件事

你被交付了兩個檔案：**這份 .md（規則）** 與 **同名 .xlsx（狀態）**。交付你的人只會說一句話：
「**你是開發者**」或「**你是驗證者**」。其餘一切從這兩個檔案自己讀出來。

| 你被告知的身分 | 先做這件事 | 然後跳到 |
| --- | --- | --- |
| **開發者**（修復方） | 打開 xlsx → 「缺陷登記」分頁，篩出**狀態 = 新開／複驗未過**的列 | **§4 開發者 SOP** |
| **驗證者**（檢驗方） | 打開 xlsx → 「缺陷登記」分頁，篩出**狀態 = 待複驗**的列；若一張都沒有，改看「測試案例」分頁**狀態 = 未測**的列 | **§5 驗證者 SOP** |
| 都不是（owner／PM） | 看「輪次彙總」的『累計未結案』與「結案簽核」的條件 | **§10 結案簽核** |

> 兩位執行者都假設具備前後端開發經驗，所以本文件**不解釋基礎技術**，只規定**流程、欄位權責與證據標準**。

## 3. xlsx 使用方式（逐分頁：誰填、填什麼、不准動什麼）

| 分頁 | 內容 | 權責 |
| --- | --- | --- |
| **說明** | 文件資訊、三方分工、狀態定義、結案四條件的摘要 | 唯讀（與本 .md 同步，以 .md 為準） |
| **測試案例** | 120 題的期望值與步驟；初驗（R1）結果、關聯缺陷、目前狀態、最終判定 | **驗證者**填 I～N 欄（R1 實測結果／R1 判定／關聯缺陷／目前狀態／最終判定／備註）。**開發者不改這裡** |
| **缺陷登記** | 每張缺陷一列：標題、嚴重度、分類、發現輪次、重現步驟、根因、目前狀態、結案輪次 | **驗證者**開單並填 A～G 欄；**開發者**填 H 欄（根因）；**狀態欄 I 兩人都會改**，改的時機見 §3 狀態表 |
| **來回記錄** | **一列 = 一輪**。左半橘色 = 開發者；右半藍色 = 驗證者 | **開發者**只填 E～L 欄（問題判定／根因／為何沒被攔到／修法／同類掃描／測試與變異測試／commit／自檢證據）；**驗證者**只填 M～R 欄（複驗方式／判讀邏輯／實測結果／判定／未解或新增／執行人日期）；A～D（輪次／缺陷 ID／關聯案例／日期）由**先動手的那一方**建立 |
| **輪次彙總** | 每輪一列的統計與結論；『本輪新增／結案缺陷／累計未結案』是公式 | **驗證者**在每輪複驗結束時填該列（日期、版本、各判定數、是否回歸、結論） |
| **交接紀錄** | 每次交接一列：誰交給誰、版本、對方該做什麼 | **交出檔案的那一方**填，交出前最後一個動作 |
| **還原檢查** | R-1～R-10 的環境還原清單 | **驗證者**每個測試時段結束時填 |
| **結案簽核** | 結案五條件、自動統計、三方簽名 | 三方各簽自己那列；統計欄是公式 |

### 3.1 從 xlsx 判讀「現在該做什麼」

開工前先用這張表把「現在輪到誰、該做什麼」讀出來。**先看缺陷登記，再看測試案例。**

| 缺陷登記 · 目前狀態 | 意思 | 輪到誰 | 該做什麼 | 做完把狀態改成 |
| --- | --- | --- | --- | --- |
| `新開` | 驗證者剛開單，還沒人修 | **開發者** | 定位根因 → 修 → 補測試 → 部署 | `待複驗` |
| `修復中` | 開發者已受理，作業中 | **開發者** | 同上 | `待複驗` |
| `待複驗` | 已部署，等黑箱複驗 | **驗證者** | 重放原始重現步驟 → 黑箱複驗 → 寫判讀邏輯 | 通過 → `結案`；不通過 → `複驗未過` |
| `複驗未過` | 複驗打回 | **開發者** | 看驗證者寫的「未解」欄，重修（**通常是修了實例沒修類別**） | `待複驗`（輪次 +1） |
| `待裁定` | 規格未定，需 owner 決定 | **Owner** | 裁定並把理由寫進缺陷登記的備註 | `結案` 或 `非缺陷` |
| `結案` / `非缺陷` | 已完成 | — | — | — |

| 測試案例 · 目前狀態 | 輪到誰 | 該做什麼 |
| --- | --- | --- |
| `未測` | **驗證者** | 依該列的步驟執行，填 R1 實測結果與判定 |
| `FAIL` / `OBSERVE` | **驗證者** | 到「缺陷登記」開一張 DEF，把編號填回「關聯缺陷」欄 |
| `待複驗` | **驗證者** | 該案例關聯的缺陷已修好，重跑這一題 |
| `PASS` / `N/A` | — | 把「最終判定」也填上，該題完成 |

**如果缺陷登記與測試案例都沒有輪到你的列** → 你這一輪沒事做，在「交接紀錄」寫一列交回去，並說明原因。

## 4. 開發者 SOP（被告知「你是開發者」時照這個做）

> 你是修復方。你的產出不是「改好了」，而是**四件可被第三方複核的證據**。

**第 0 步 — 讀狀態（5 分鐘）**
1. 「缺陷登記」篩 `新開` + `複驗未過`，依嚴重度 高 → 中 → 低 排序。
2. 若有 `複驗未過`，**先做這些**：它代表上一輪的修法沒過關，優先級高於新缺陷。
3. 到「來回記錄」讀該缺陷**所有歷史列**，特別是驗證者的「未解／新增問題」欄——那是上一輪被打回的原因。

**第 1 步 — 定位根因到行**
- 產出要能寫成 `檔案路徑:行號` + 一行程式碼。寫「XX 模組的邏輯問題」等於沒定位，驗證者會直接打回。
- 填到「缺陷登記」的 **H 欄（根因）**。

**第 2 步 — 判斷這是實例還是類別**（這一步決定你會不會被打回）
- 問自己：**同一種寫法在這個 repo 還有幾處？** 用掃描（grep／AST／自寫腳本）給出數字，不要靠讀。
- 把掃描結果寫進「來回記錄」的 **H 欄（修法）**：同類共 N 處，其中 M 處一併修、K 處列白名單並寫明理由。
- 只修被點名的那一處 → 驗證者判 `複驗未過`。本專案前一次稽核就因此多花了兩輪。

**第 3 步 — 補一個會失敗的測試，並自己做變異測試**
- 先寫測試、讓它在**修復前的程式碼**上失敗，再修程式讓它通過。
- 把「改回舊寫法 → 哪幾則測試失敗、訊息是什麼」寫進「來回記錄」的 **J 欄**。
- ⚠ 如果這個缺陷**原本就有守門測試卻沒攔到**，你還要回答：**為什麼沒攔到**，並修掉測試本身的盲點。填「來回記錄」的 **G 欄（為何沒被攔到）**。這是本專案吃過最大的虧。

**第 4 步 — 部署並自檢**
- 部署到受測環境，記下 commit（填 **K 欄**）。
- 跑靜態檢查與測試套件，把結果填 **L 欄（自檢證據）**：lint／型別檢查／測試通過數。
- **自檢數字不是複驗結果**，驗證者不會採信，但缺了它代表你沒跑。

**第 5 步 — 交回**
1. 「缺陷登記」狀態改 `待複驗`。
2. 「來回記錄」新增一列（或補完既有列的左半），輪次用目前這一輪。
3. 「交接紀錄」寫一列：交給驗證者、部署版本、請他複驗哪幾張缺陷。
4. **不要動**「測試案例」分頁、驗證者的欄位、以及本 .md。

**開發者的禁止事項**
- 不要自己把缺陷改成 `結案`——只有驗證者複驗通過才能結案。
- 不要修改測試案例的「預期結果與驗算」欄來讓案例通過。期望值要改必須走 owner 裁定。
- 不要在同一輪裡**順手**改與缺陷無關的東西；那會讓回歸無法歸因。要改另開一張缺陷。

## 5. 驗證者 SOP（被告知「你是驗證者」時照這個做）

> 你是檢驗方。你的立場是：**任何沒有被你親手重現過的結論都不成立**，包括開發者的自檢數字，也包括你自己上一輪的結論。

**第 0 步 — 讀狀態（5 分鐘）**
1. 「缺陷登記」篩 `待複驗`；沒有的話看「測試案例」的 `未測`。
2. 「交接紀錄」看最後一列：對方部署的版本是什麼、要你複驗哪幾張。
3. **先確認受測站版本**＝對方說的 commit。版本不符就停下來，在交接紀錄寫明並交回。

**第 1 步 — 黑箱執行**
- 用**真實瀏覽器**走使用者會走的路徑，不要直接打 API 就算數（API 只用來做數值逐位比對）。
- 依測試案例的「操作步驟」逐步做；會寫入的案例**先記基準**（§9 通用規則第 1 條）。
- **重放原始重現步驟**：複驗一張缺陷時，做的必須是當初讓它 FAIL 的那串操作，不是開發者建議你看的地方。

**第 2 步 — 寫判讀邏輯（本專案的硬性要求）**
每一個 `FAIL`、每一次複驗，都要在「來回記錄」的 **N 欄（判讀邏輯）** 按這個結構寫：

```
觀察：我看到什麼（含實際數值／截圖編號）
假設：可能的原因有哪些（至少兩個）
排除：我怎麼排除「是我自己量錯」——換一種方式再測一次
定位：證據指向哪裡（畫面／API 回應／必要時才看原始碼）
判定：PASS / FAIL / 複驗未過 / OBSERVE，以及為什麼
```

> 「排除」這一步不是形式。本專案前一次稽核，檢驗方一開始誤報過「按鈕沒反應」（其實是用了錯的偵測方式）、「圖表沒切換」（等待時間不夠）、「刪除沒有確認框」（彈窗用 `position:fixed`，`offsetParent` 讀不到）。**在指控系統壞掉之前，先證明不是自己的量測方法壞掉。**

**第 3 步 — 複驗一張缺陷時，四條結案條件逐條查**
1. 根因有沒有寫到**行**？沒有 → `複驗未過`。
2. 修的是類別還是實例？**自己抽驗一次同類**：挑開發者沒點名的地方，看同樣的問題還在不在。
3. 變異測試：**自己重做一次**——把修復前的寫法放回去（本機副本即可），確認那些測試真的會失敗。開發者說會失敗不算。
4. 黑箱重放通過，且**跑一次 J 組回歸快篩**確認沒有把別的東西弄壞。

**第 4 步 — 記錄結果**
- 「來回記錄」右半：複驗方式／判讀邏輯／實測結果（**含數字**）／判定／未解或新增問題／執行人日期。
- 通過 → 「缺陷登記」狀態改 `結案`、填結案輪次；同時把「測試案例」該題的**最終判定**填 `PASS`。
- 不通過 → 狀態改 `複驗未過`，在「未解」欄寫清楚**還差什麼**（不是重複貼原問題）。
- 複驗中**新發現**的問題 → 開新的 DEF，發現輪次寫當前輪次。這是正常的，不是失敗。
- 每輪結束填「輪次彙總」一列，並跑「還原檢查」R-1～R-10。

**第 5 步 — 交回**
「交接紀錄」寫一列：交給開發者、本輪結論、請他處理哪幾張缺陷。

**驗證者的禁止事項**
- 不要改「預期結果與驗算」欄來遷就實作。實作與期望不符就是 FAIL 或 OBSERVE。
- 不要只寫「正常／不正常」。沒有數字的結果視同沒測。
- 不要因為「上一輪驗過了」就跳過重放。每一輪都是從零開始。
- 不要在同一輪內一邊測一邊讓對方改；一輪就是一次交付、一次複驗。

## 6. 判讀邏輯的書寫規範（驗證者必填、開發者必看）

兩邊都要留下「**為什麼這樣判**」，否則下一輪的人無法接手。

**驗證者填「來回記錄 · N 欄（判讀邏輯）」，五行結構：**

| 行 | 要寫什麼 | 反例（會被退回） |
| --- | --- | --- |
| 觀察 | 看到的現象＋**實際數值** | 「怪怪的」 |
| 假設 | 至少兩個可能原因 | 只寫一個，等於已經先射箭再畫靶 |
| 排除 | 換一種方式再測一次，排除是自己量錯 | 沒有這一行 → 退回 |
| 定位 | 證據指向哪裡（畫面／API／必要時才看原始碼） | 「應該是後端的問題」 |
| 判定 | PASS／FAIL／複驗未過／OBSERVE ＋ 理由 | 沒有理由 |

**開發者填「來回記錄 · G 欄（為何沒被攔到）」，回答三件事：**
1. 這個缺陷原本**應該**被哪一道防線攔下（型別檢查／單元測試／守門測試／程式審查）？
2. 那道防線為什麼沒攔到？（規則太窄？清單是手寫的？根本沒有這道防線？）
3. 這一輪你怎麼補上？補完之後，**同樣的漏法**下次會被攔下嗎？

> 真實範例（本專案）：帳戶名稱雙軌的守門測試，檔案清單是**手寫**的，漏了 `broker-import.js`；中文標點的守門測試，規則只抓**緊貼**中文字的半形標點，而出問題那行的標點後面都空一格。兩者當時都是綠燈。修法分別是「改成自動掃描所有相關檔案」與「規則放寬為緊貼或只隔空白」。

## 7. 缺陷結案的四個條件（驗證者逐條查，全過才可結案）

| 條件 | 說明 |
| --- | --- |
| **1. 根因定位到行** | 缺陷登記的「根因」欄必須寫到**檔案:行**，不能只寫現象或模組名 |
| **2. 修類別不修實例** | 修復方必須附上**同類掃描結果**（例如：全語料/全檔案掃過一遍，同類還有幾處、各自怎麼處理）。只修被點名的那一處 → 檢驗方應判『複驗未過』 |

### 嚴重度與分類

| 嚴重度 | 判準 |
